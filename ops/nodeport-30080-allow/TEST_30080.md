# NodePort 30080 적용·양성/음성/롤백 시험 (P1-SEC-01 #19)

대상 AC: [#19](https://github.com/321Team/fds-project-baseline/issues/19) "`.50/32→Worker:30080`만 preDNAT 허용".
Exit Criteria 요구: Positive·Negative·Rollback Evidence.

**edge01 nginx upstream은 바꾸지 않는다.** edge01에서 `curl`로 Worker:30080을 직접 호출해 시험한다. 서비스 트래픽 영향 없음.

## 전제 (2026-09-26 조회)

| 항목 | 값 |
|---|---|
| GNP `nodeport-30080-allow` | 현장 존재, spec = `nodeport-30080-allow.yaml` |
| Worker HEP 라벨 | worker01~03 `fds.example/role=worker` |
| transaction-api Pod | worker01(.105), worker02(.107). worker03(.108) 없음 |
| 기존 30080 사용 Service | 없음 |

`externalTrafficPolicy: Local`이므로 **Pod가 있는 Worker만 응답**한다. Pod 배치가 바뀌었으면 기대값 표를 그 배치에 맞춰 다시 쓴다.

## 0. 적용 직전 확인 (k8s-control01)

```bash
cd ~/infra-kubernetes/ops/nodeport-30080-allow   # 또는 repo-root 기준 전체 경로
K="sudo kubectl --kubeconfig=/etc/kubernetes/admin.conf"
$K -n fds-app get svc transaction-api -o jsonpath='{.spec.ports}{"\n"}'   # http 80 → targetPort 8000 인지
$K -n fds-app get pod -l app=transaction-api -o wide                       # 배치·Pod 이름·Node 재확인
$K get svc -A | grep 30080 || echo "30080 미사용"
$K diff -f transaction-api-nodeport.yaml; echo "rc=$?"                     # 신규 생성만 나와야 함
```
기존 Service의 targetPort가 8000이 아니면 **중단**하고 YAML을 고친다.
`get pod -o wide`의 Pod 이름·Node는 2단계 로그 확인에 사용하므로 기록해 둔다.

## 1. 적용 (k8s-control01)

```bash
date; $K apply -f transaction-api-nodeport.yaml
$K -n fds-app get svc transaction-api-nodeport -o wide
$K -n fds-app get endpointslices -l kubernetes.io/service-name=transaction-api-nodeport -o wide
```

## 2. 양성 — edge01(10.1.93.50)에서 + Pod 관측 Source IP 확인 (B1)

D18(`externalTrafficPolicy: Local`)의 인수조건은 HTTP 200뿐 아니라 **Pod가 실제로 관측하는 L3 Source IP가 10.1.93.50인지**다. HTTP 코드만으로는 이걸 증명하지 않으므로 curl과 Pod access log 수집을 같은 시간창에서 같이 한다.

```bash
# edge01(10.1.93.50)에서
date  # 시작 시각 T0 기록
for ip in 10.1.93.105 10.1.93.107 10.1.93.108; do
  printf '%s %s ' "$(date +%T)" "$ip"; curl -s -m 5 -o /dev/null -w '%{http_code}\n' "http://$ip:30080/readyz"
done
date  # 종료 시각 T1 기록
```

```bash
# k8s-control01에서, T0~T1 사이만
$K -n fds-app get pod -l app=transaction-api -o wide     # Pod 이름·Node 재확인(0단계와 비교)
$K -n fds-app logs <transaction-api Pod on worker01> --since-time="<T0 ISO8601>" | grep -F "/readyz"
$K -n fds-app logs <transaction-api Pod on worker02> --since-time="<T0 ISO8601>" | grep -F "/readyz"
```
transaction-api는 Uvicorn 기본 access log가 켜져 있어 별도 debug container 없이 확인 가능하다. 기대 로그 형태: `10.1.93.50:<ephemeral-port> - "GET /readyz HTTP/1.1" 200`.

| 대상 | 기대(HTTP) | 기대(Pod 로그 remote addr) | 이유 |
|---|---|---|---|
| .105 worker01 | `200` | 해당 Pod 로그에 `10.1.93.50:*` 기록 | Pod 있음, Local이 source 보존 |
| .107 worker02 | `200` | 해당 Pod 로그에 `10.1.93.50:*` 기록 | Pod 있음, Local이 source 보존 |
| .108 worker03 | `000`(응답 없음) | 로그 없음(당연) | Pod 없음 + Local. 방화벽 차단이 아님 |

**판정 조건 (필수):** worker01·worker02 Pod 로그의 remote address가 `10.1.93.50`이 **아니면 FAIL/STOP**으로 기록하고, GNP/Service 인수를 진행하지 않는다. edge의 X-Forwarded-For가 아니라 TCP 연결의 실제 remote address를 봐야 한다.

## 3. 음성 — .50이 아닌 출발지 2곳 + 대조군 (B2)

`000`만으로는 "GNP Deny가 동작한 것"과 "그 출발지에서 Worker로 가는 경로 자체가 끊긴 것"을 구분할 수 없다(특히 ansible01은 다른 subnet). 각 출발지에서 30080 시험 **직전에** 현재 승인되어 있는 기존 경로로 대조군을 확인하고, 대조군이 성립할 때만 30080 결과를 판정에 쓴다.

```bash
# ansible01(10.250.10.10)에서 — 대조군: Worker SSH(v4 host GNP로 이미 허용된 경로)
for ip in 10.1.93.105 10.1.93.107 10.1.93.108; do
  printf '%s %s ctrl-ssh ' "$(date +%T)" "$ip"; nc -zv -w3 "$ip" 22 2>&1 | tail -1
done
# 위 대조군이 전부 성공했을 때만 아래 30080 시험을 진행
for ip in 10.1.93.105 10.1.93.107 10.1.93.108; do
  printf '%s %s 30080 ' "$(date +%T)" "$ip"; curl -s -m 5 -o /dev/null -w '%{http_code}\n' "http://$ip:30080/readyz"
done
```

```bash
# k8s-control01(.102)에서 — 대조군: Worker kubelet(10250, 컨트롤플레인이 상시 사용하는 기존 경로)
for ip in 10.1.93.105 10.1.93.107 10.1.93.108; do
  printf '%s %s ctrl-kubelet ' "$(date +%T)" "$ip"; nc -zv -w3 "$ip" 10250 2>&1 | tail -1
done
# 위 대조군이 전부 성공했을 때만 아래 30080 시험을 진행
for ip in 10.1.93.105 10.1.93.107 10.1.93.108; do
  printf '%s %s 30080 ' "$(date +%T)" "$ip"; curl -s -m 5 -o /dev/null -w '%{http_code}\n' "http://$ip:30080/readyz"
done
```

| 대상 | 대조군 기대 | 30080 기대 |
|---|---|---|
| .105 / .107 / .108 (ansible01) | SSH(22) 연결 성공 | 모두 `000`(시간 초과). Pod가 있는 .105/.107도 막혀야 GNP Deny가 동작한 것 |
| .105 / .107 / .108 (k8s-control01) | kubelet(10250) 연결 성공 | 모두 `000`(시간 초과) |

**판정 조건:** 대조군이 하나라도 실패하면 그 출발지의 30080 음성 판정은 **INCONCLUSIVE**로 남기고(경로 자체가 끊겨 있어 GNP 효과인지 알 수 없음), 원인(경로 장애)을 따로 기록한다. 단순 ping 성공은 TCP 경로 대표로 쓰지 않는다.

## 4. 롤백 — Service 삭제 후 원복

```bash
# k8s-control01
date; $K -n fds-app delete svc transaction-api-nodeport
# edge01: 2번 for 명령 → .105/.107도 000 이어야 함 (30080 닫힘)
# k8s-control01: 재적용
date; $K apply -f transaction-api-nodeport.yaml
# edge01: 2번 for 명령 → .105/.107 200 복귀
```
GNP는 롤백 대상이 아니다(9/22부터 현장 존재, 30080 Service가 없으면 영향 없음).

## 5. 기록

각 단계의 `date`와 출력(HTTP 코드, Pod 로그 remote addr, 대조군 결과)을 #19에 남긴다. 판정 표:

| 시험 | 기대 |
|---|---|
| 양성(.50) HTTP | Pod 있는 Worker `200` |
| 양성(.50) Pod 로그 remote addr (B1) | worker01·worker02 Pod 로그에 `10.1.93.50:*` — 아니면 FAIL/STOP |
| 음성 대조군 (B2) | ansible01→SSH(22), k8s-control01→kubelet(10250) 모두 성공 — 실패 시 해당 출발지는 INCONCLUSIVE |
| 음성(.102, 10.250.10.10) 30080 | 대조군 성공 전제로 전부 `000` |
| 롤백(삭제) | .50에서도 `000` |
| 롤백(재적용) | .50에서 `200` 복귀, worker01·worker02 Pod 로그에 `10.1.93.50:*` 재확인 |

## 범위 밖

- edge의 Worker별 `/readyz` 점검 구성(D18 Local 전제) — upstream 교체 때 함께 한다
