# Node Runtime 인가 기록의 신뢰 경계

2026-09-14 / PR #4 리뷰 B3에 대한 설계 설명. 실행 승인 기록이 아니다.

## 의도와 한계

`validate_authorization_record()`는 이 변경에 지정된 실행자 `GWONUK`과 독립 검토자 `hayeounglee`, 승인된 source/target/mode, 검토 URL, 실행 조건, 입력·정책 해시와 작업창을 대조한다. 이름 비교는 다른 담당자의 기록이나 잘못된 실행 입력을 혼용하지 않게 하는 **기록 일관성 검사**다.

인가 JSON을 편집할 수 있는 사람은 이름과 `APPROVED`, 조건의 `true` 값을 작성할 수 있다. SHA-256도 함께 다시 계산할 수 있다. 따라서 이 검사는 사용자 인증, 전자서명 검증, GitHub API의 승인 조회, 위조 방지 또는 역할 기반 접근통제를 제공하지 않는다. 같은 JSON에 역할 목록을 추가하고 그 값을 신뢰하는 것으로 이 한계를 해결할 수 없다.

지정 이름은 코드의 `EXPECTED_OPERATOR` / `EXPECTED_REVIEWER`에 유지한다. 범용 IAM 역할로 자동 확장하지 않는다. 담당자 변경은 코드·절차 검토를 거쳐 반영하며 기존 실행의 승인·복구 기록을 다른 이름으로 덮어쓰지 않는다.

## 실제 실행 전 대조

1. 실행자가 해당 PR 또는 실행 결정 페이지를 인증된 GitHub 세션에서 직접 열고 작성자, 최종 판정, 검토 HEAD와 이후 변경 여부, 정확한 대상·작업창·잔여 조건을 확인한다. URL 문자열이 형식에 맞는 것만으로 완료 처리하지 않는다.
2. 독립 검토자는 보호·복구 계획과 원본 증적을 실제로 열어 지정 해시 및 현장 조건을 대조한다. 원본 미전달, 검토 보류, 만료된 입력 또는 다른 HEAD 승인인 경우 실행하지 않는다.
3. 확인된 결정을 별도 승인 파일에 연결하고 해당 파일의 해시를 기록한다. CP1 최종 Runtime 영수증과 Positive/Negative/Regression 인수 조건도 실제 증적으로 충족해야 한다.
4. 서버 접근은 기존 SSH 키·known_hosts·호스트 사용자·sudo·소스 경로/권한 검사로 제한한다. 이 접근 경계와 GitHub의 독립 검토는 서로 다른 통제다. 승인된 sudo 권한을 가진 악의적인 운영자를 이 오프라인 기록 검사로 차단한다고 주장하지 않는다.

## 변경하지 않은 범위

이번 보완은 기존 이름·승인·해시·작업창 검사를 약화하지 않는다. JSON이 실제 승인 사실을 증명한다는 가정을 제거하고 사람이 수행할 대조를 명시한다. 온라인 GitHub 검증이나 서명된 인가를 도입하려면 발급자·키/토큰 관리·가용성·폐기·오프라인 복구를 포함한 별도 설계가 필요하다. 이번 PR에 인증 기능을 구현한 것으로 기록하지 않는다.
